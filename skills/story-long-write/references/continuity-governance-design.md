# 长篇小说一致性与修改治理系统设计

> 版本：1.0  
> 状态：已落地  
> 范围：任意长篇小说项目，不绑定具体书名、角色或题材。  
> 执行细则：revision-impact-and-canon.md、workflow-revision.md、tracking-transaction.md。

## 1. 设计目标

长篇修改不是改完一个文件就结束。一处身世、血缘、规则或终局变化，可能同时影响正文、细纲、卷纲、总纲、角色设定、关系、时间线、伏笔和后续章节。

本系统要求：**修改前算出影响范围，修改中逐项裁决冲突，修改后用结构化状态与门禁证明已经闭环。**

## 2. 工具与作品解耦

| 层级 | 允许保存 | 禁止保存 |
|---|---|---|
| 通用工具 skills/ | Schema、类别、扫描算法、门禁、通用示例 | 具体书名、角色名、剧情事实、项目默认值 |
| 作品源文件 | 该书的设定、总纲、卷纲、细纲、正文 | 其他作品事实 |
| 作品追踪目录 | 该书当前状态、长期事实、关系、伏笔、时间线 | 手写派生视图、跨书共享事实 |

通用工具只能通过 “--project {作品根目录}” 读取当前作品；每本书拥有独立的事实 ID 和状态修订号。

## 3. 三类权威

| 权威 | 内容 | 冲突处理 |
|---|---|---|
| 设计权威 | 设定、总纲、卷纲、细纲 | 表达作者计划，不能默认覆盖已发表正文 |
| 读者事实 | 正文 | 已被读者看见；要么正式回修正文，要么调整设计 |
| 结构化当前事实 | 追踪/_tracking-state.json | 续写与审查的机器权威，只能通过事务更新 |

所有追踪 Markdown 都由结构化状态生成，禁止手改。

## 4. 系统流程

~~~text
修改请求
   ↓
影响计划：改什么＋实体＋事实 ID＋章节
   ↓
自动生成必查清单
   ├─ N-1 / N / N+1 正文与细纲
   ├─ 总纲、卷纲与相关设定
   ├─ 命中受影响实体的正式工件
   └─ 长期事实、关系清单、实体档案、角色快照
   ↓
逐项阅读＋登记 S1—S4 冲突
   ↓
统一修改源工件＋更新结构化事实
   ↓
修改影响门禁＋追踪一致性门禁
   ↓
允许交付、发布修订章或继续写新章
~~~

## 5. 长期事实与关系清单

### 5.1 收录什么

- 身份、血缘、亲属、婚姻、别名、传承、从属、长期合作或敌对；
- 核心物件、证据、产业的所有权或保管权；
- 世界规则、机构权限、系统代价、不可逆状态；
- 决定当前因果的历史事实。

一次性对话、短期情绪、当前站位和普通出场不进长期事实层。

### 5.2 每条事实的结构

| 字段 | 作用 |
|---|---|
| id | K### 为硬事实，R### 为关系；修改始终指向同一 ID |
| category | 身份、血缘、亲属、婚姻、传承、所有权、规则、权限等 |
| subject / predicate / object | 主体—断言—客体的最小事实单元 |
| cardinality | one 为单值槽位，many 为多值槽位 |
| canon_status | 锁定设定或正文已证 |
| reader_status | 未揭示、部分揭示、已揭示 |
| reveal_chapter | 读者实际知道该事实的章节 |
| established_chapter | 事实在故事中成立的章节 |
| evidence | 可核验的正文、设定或大纲来源 |
| related_entities | 生成关系邻接和修改影响扩散 |
| negative_constraints | 明写禁止误读，阻止似是而非的改写 |

### 5.3 三张关系视图

1. 设定/关系.md：作者设计层，可包含尚未发生的未来关系。
2. 追踪/关系清单.md：按 R### 生成的当前关系总表。
3. 追踪/事实档案/{实体}.md：聚合某个人物、机构或物件相连的全部事实。

后两张是派生视图，不得手改。修改一个人物时，先打开其事实档案，再沿 related_entities 查到相邻人物、祖辈、后代、机构和物件。

### 5.4 自动冲突约束

- 相同主体—断言—客体不得用不同 ID 重复登记；
- one 槽位不得同时存在两个不同客体；
- 关系事实必须有相关实体和证据；
- 未揭示事实不得伪装成读者已知；
- 派生关系表被手改后，一致性检查必须失败。

## 6. 修改影响矩阵

| 修改起点 | 必查向上权威 | 必查同层 | 必查向下投影 |
|---|---|---|---|
| 正文第 N 章 | 对应细纲、卷纲、总纲、相关设定 | N-1/N+1 正文 | 后续命中实体或事实的正文与细纲 |
| 细纲第 N 章 | 卷纲、总纲、相关设定 | N-1/N/N+1 细纲 | 已存在的第 N 章正文和受承诺影响的后续章 |
| 卷纲 | 总纲、题材与角色/世界设定 | 相邻卷交接 | 该卷细纲、正文、伏笔与人物弧 |
| 总纲或终局 | 题材契约、世界底牌 | 主线、辅线、人物弧 | 所有受影响卷纲、细纲、正文和长期事实 |
| 角色、身世、关系 | 总纲与已发表正文 | 关系图中的直接相连实体 | 命中实体的卷纲、细纲、正文和事实档案 |
| 世界规则、权限、物权 | 总纲与题材契约 | 相关机构、持有人和代价 | 所有使用或见证该规则的正文与细纲 |

路径中带“备份”“归档”或 archive(s) 的历史副本不是当前事实源，不进入影响清单，也不能作为修订起点。

## 7. 修改计划

每次语义修改必须先声明：

~~~json
{
  "change_id": "本次修改的唯一标识",
  "summary": "要改变的语义",
  "semantic_change": true,
  "changed_files": ["本轮要修改的源文件"],
  "affected_entities": ["受影响的人物、机构或物件"],
  "affected_fact_ids": ["R001", "K001"],
  "affected_chapters": [1]
}
~~~

revision_guard.py plan 根据声明重算 required_checks。修改者不能通过少报实体、事实 ID 或章节来跳过扫描。

## 8. 冲突登记与裁决

| 字段 | 含义 |
|---|---|
| source / target | 发生冲突的两个工件 |
| severity | S1 根本设定/血缘/因果；S2 连续性/伏笔/规则；S3 局部；S4 表达 |
| issue | 具体冲突事实 |
| resolution | 保留哪个口径、修改哪些地方及原因 |
| status | resolved、accepted 或 unresolved |

裁决规则：

- unresolved 一律阻断；
- S1/S2 不得用 accepted 保留矛盾，必须修复；
- 正文与设计冲突时，必须明确选择“回修正文”或“调整设计”；
- “以后注意”不算解决方案；已经发现的反向口径必须本轮统一。

## 9. 六道门禁

| 门禁 | 通过条件 |
|---|---|
| G0 源文件门 | 只修改正式设定、大纲和正文，不以备份或派生视图为起点 |
| G1 影响计划门 | required_checks 由工具重算且没有被手工缩减 |
| G2 必查清单门 | 每个必查文件都进入 checked_files |
| G3 冲突闭环门 | 无 unresolved，所有 S1/S2 均已真正修复 |
| G4 结构化追踪门 | 语义修改已通过 commit 或 migrate-v4 推进 state_revision |
| G5 派生一致性门 | tracking_commit.py check 证明全部派生视图与权威状态一致 |

涉及中文正文时，再叠加语言门、去 AI 味门和退化检查；文本质量门不能替代一致性门。

~~~text
修改完成 = 影响清单无漏项
         AND 冲突全部闭环
         AND 结构化事实已推进
         AND 派生视图一致
         AND（如有正文）正文质量门通过
~~~

## 10. 标准修改流程

1. 把需求写成一句可验收的语义目标。
2. 调用 `revision-governor phase=plan`，据其影响分析声明源文件、实体、事实 ID 和章节，再运行 revision_guard.py plan 生成活动清单。
3. 阅读全部 required_checks，登记 checked_files 与 conflicts。
4. 先裁定最终口径，再统一修改正文、细纲、卷纲、总纲和设定。
5. 重新扫描影响集，纳入新出现的实体或章节。
6. 用追踪事务更新角色快照、伏笔、时间线和 fact_changes。
7. 调用 `revision-governor phase=verify`；通过后运行带摘要审批戳的 revision_guard.py check 与 tracking_commit.py check。
8. 如有正文，再运行语言、去 AI 味和退化门。全部通过后才能声称完成。

## 11. 日常续写如何召回几十章前的信息

1. 读取追踪/上下文.md 恢复热状态。
2. 读取下一章细纲，提取本章实体与事实 ID。
3. 定点读取对应事实档案、关系清单、角色快照、活跃伏笔和时间线。
4. 只对必须核验的旧事实回读原始证据章。

因此不依赖聊天记忆，也不需要每章重读整书。

## 12. 通用例子：修改身世关系

若把“角色甲的生父是角色乙”改为“角色丙”：

1. 该关系使用稳定 R###，且“生父”是 one 槽位。
2. 影响实体至少包含甲、乙、丙，并扩散到兄弟姐妹、祖辈、后代、姓氏和继承权。
3. 必查总纲、卷纲、细纲、已发表正文、角色卡、时间线、伏笔、关系清单与三人的事实档案。
4. 如果正文已经明确角色乙，必须正式回修正文或放弃修改，不能只改角色卡。
5. 新旧客体同时存在时，单值事实门直接拒绝提交。
6. S1/S2 全部修复、追踪推进并通过双检查后才算完成。

## 14. 验收标准

- 通用工具不含具体作品事实；
- 每条长期事实都有 ID、证据、读者状态和禁止误读；
- 关系总表与实体档案自动生成；
- 单值事实冲突在写入前被拒绝；
- 正文、细纲、卷纲、总纲、设定的语义修改都走同一流程；
- 必查文件未读、冲突未解、追踪未推进或派生视图不一致时，修改不能通过。
