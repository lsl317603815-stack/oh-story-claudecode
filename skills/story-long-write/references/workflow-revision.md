# workflow-revision.md：跨产物大修工作流

本文件为"大修/回炉/设定调整"场景的完整指引。SKILL.md 路由到本文件后，必须同时完整读取 [revision-impact-and-canon.md](revision-impact-and-canon.md)，按以下流程执行。

---

## 适用条件

- 用户说"修改第X章""回炉第X章""重写第X章"
- 用户要修改总纲、卷纲、细纲、角色/身世/关系设定、世界规则、物权、机构权限或终局口径
- 目标：修改源产物并沿“设定/总纲 ↔ 卷纲 ↔ 细纲 ↔ 正文 ↔ 结构化追踪”闭环所有受影响投影

> 用户必须能说明要改的事实或源文件；不再限于章号。影响章节由 `revision_guard.py plan` 展开，不靠印象手列。

## Step 1：建立修订影响清单

1. 执行 `tracking_commit.py check`，记录修订前 `state_revision`。
2. **修改前调用 `revision-governor`，`phase=plan`**：把修改意图、目标源文件、`last_committed_chapter/state_revision` 和已知实体/事实/章节交给它。只有返回 `READY_TO_PLAN` 才能继续；agent 不可用时由主线程按同一角色卡 solo 执行并明确报告 fallback，不能跳过影响分析。
3. 以治理结果为输入，列出本轮 `changed_files / affected_entities / affected_fact_ids / affected_chapters`，按 [revision-impact-and-canon.md](revision-impact-and-canon.md) 运行 `revision_guard.py plan`，固定输出到 `追踪/修改影响/active.json`。没有这个活动清单，hooks 会拒绝修改已提交正文和既有大纲/设定。
4. 在修改前读完 `required_checks` 中的上下级大纲、相邻章、设定、长期事实/关系和实体档案。
5. 修订过程中新发现的受影响实体/章节或源文件必须先停笔，补回计划并重生成 `active.json`，再继续修改；不能事后手填，也不能留在口头待办。

---

## Step 2：定位源产物与事实槽位

1. 根据"第X章"找到文件：`正文/第{X}章_*.md`
2. 如果用户说的是章节名而非编号，用 `find 正文/ -name "*{关键词}*"` 搜索
3. 找不到时让用户确认具体章节
4. 如果用户指定段落范围（"第3-5段"/"那场打斗"/"对话部分"），记录为局部修改目标
5. 非正文修订按实际文件定位；如涉及身世、关系、所有权、权限或不可逆规则，同时定位 `长期事实.md` 中的主体+断言槽位和相关 ID；索引中尚无此事实时创建新 ID，不以无 ID 为理由跳过。

---

## Step 3：加载上下文

加载比日常写作更多的上下文（因为修改需要理解前后衔接）：

| 序号 | 文件 | 用途 | 如果不存在 |
|------|------|------|-----------|
| 1 | `正文/第{X}章_*.md` | 待修改章节 | 必须存在 |
| 2 | `大纲/细纲_第{X}章.md` | 原始写作计划 | 跳过 |
| 3 | `正文/第{X-1}章_*.md` | 前一章（衔接） | 第1章时加载 `设定/世界观/背景设定.md` 替代 |
| 4 | `正文/第{X+1}章_*.md` | 后一章（衔接） | 末章时检查 `大纲/细纲_第{X+1}章.md`（如有）确保连续性 |
| 5 | `tracking_commit.py check` + `追踪/上下文.md` | 用工具确认唯一 state 与派生视图一致；续写状态卡提供当前连续性，不把完整 state 加入 prompt | 缺 state 时停止；已有正文项目必须经 `story-import` 生成标准追踪状态 |
| 6 | `设定/角色/{相关角色}.md` + `追踪/角色状态/{相关角色}.md` | 静态人设 + 动态当前快照 | 动态快照缺失时从相关增量重算 |
| 7 | `追踪/长期事实.md` + `追踪/关系清单.md` + `追踪/事实档案/{实体}.md` | 身世/血缘/规则/物权/权限与禁止误读 | 无对应条目时根据正文/锁定设定在本轮追踪事务补建 |
| 8 | 影响清单中其余 `required_checks` | 总纲↔卷纲↔细纲↔正文及同实体历史出现 | 不存在的计划产物可标证据缺口；已存在的文件不得跳过 |

**相关角色判定**：从 `大纲/细纲_第{X}章.md` 中提取角色名。如果细纲不存在，从待修改章节正文中搜索 `设定/角色/` 目录下的角色名关键词。将角色名映射为文件名：`设定/角色/{角色名}.md`。

## Step 4：修改

1. **阅读原文**：读完整章内容，记录原始字数
2. **备份原文**：需要可回退时把本轮源产物放入项目 `备份/{YYYY-MM-DD}_{修订名}/`，不在 `正文/`、`大纲/`、`设定/` 中留会被搜索当成当前版本的“原稿”副本
3. **确认修改范围**：问用户是"全文重写"还是"修改特定段落"
   - 全文重写：基于细纲重新写，保留备份
   - 局部修改：只改指定段落（按场景序号或关键词定位），保持其他部分不变
4. **执行修改**：改写文件
5. **字数对比**：修改后与原文字数差异 > 30% 或 > 800 字时提醒用户（取较大值）

**资料研究（按需）**：如果修改涉及需要验证的外部事实（历史年代、地理方位、职业细节等），spawn `story-researcher` agent 搜索验证。

---

## Step 5：级联检查

修改完成后，用一次 `mode=revision` 追踪事务完成级联更新，协议见 [tracking-transaction.md](tracking-transaction.md)：

1. **重算修订章增量**：对比旧正文/旧增量与新正文，只保留新版本对未来仍有效的 `result / 角色变化 / 伏笔变化 / 时间与揭示 / 约束 / 下一章承诺`。事务工具整份重写 `追踪/逐章记录/第{X}章.md`，不保留被新正文推翻的结论。
2. **伏笔当前值**：对受影响 ID 从第 X 章检查到最后已写章 M，提交修订后的**截至 M 章当前状态**。若修订删除了埋设，但后文仍引用该 ID，先列为正文冲突，不能简单删除；确定整条线不存在时才用 `action=delete`。`伏笔.md` 始终每 ID 一行，不追加修订历史。
3. **时间与读者认知**：为受影响事件提交客观事实、读者截至 M 章的当前认知、实际揭示状态/章节；删掉的事件用 `action=delete`。未来揭示计划仍留大纲。工具把事件合并进 `_tracking-state.json` 并重建作者/读者视图，禁止分别手改。
4. **角色当前快照**：对受影响核心角色从 X 检查到 M，按身份、位置、目标、能力资源、关系对象、已知信息、未结事项分别重算，提交一份截至 M 的完整快照；不得用最后一条单维度变化覆盖其它维度。
5. **导入截止范围**：若 X ≤ `_tracking-state.json.imported_through_chapter`，事务为第 X 章新增覆盖记录；导入截止章不变，当前结构化状态按修订结果更新。
6. **提交与重试**：把修订开始时 `tracking_commit.py check` 返回的 `state_revision` 写入 `expected_state_revision`，再执行 `tracking_commit.py commit`；若期间状态已变化，重新读取当前状态并重构事务。任一步骤失败时保留原事务 JSON，修正写入环境后重跑同一 `commit`；成功并通过 `check` 前禁止继续修下一章或写新章。
7. **后续影响**：影响扫描结果不再只是“可能需要”的提醒。所有命中项都要进 `checked_files`；发现的冲突进 `conflicts`，本轮修正为 `resolved`。S1/S2 不得留待后续。

8. **正文元信息与中文语言锁扫描**：检查标题行以外是否混入 `第[一二三四五六七八九十百千万两0-9]+章|上一章|上章|前一章|本章|这一章|前文|后文|伏笔|细纲|读者|ch\d+ 等英文章号缩写` 这类写作工程词，以及无明确设定根据的英文句/段和裸英文词。工程词命中即改成角色当下可感知的事件锚点或相对时间；英文泄漏改成中文，只保留缩写/型号、URL/邮箱/文件名/代码与 `.deslop-whitelist` 精确登记项。故事内真实阅读/讨论“第X章”或真实读者身份语境除外。
9. **修改后调用 `revision-governor`，`phase=verify`**：把 `active.json`、实际修改文件和新修订号交给它，逐项复核影响链。返回 `BLOCKED` 时按漏改项/冲突继续修，必要时回 Step 1 重建计划；只有 `READY_TO_CLOSE` 才进机械验收。
10. **禁用词与三门禁**：对照 `references/banned-words.md` 检查修改后的内容；修订事务成功后填入 `tracking_action` 修订号，依次运行带审批戳的 `revision_guard.py check` 和 `tracking_commit.py check`。审批戳必须绑定当前 `active.json` 的摘要，清单再改即自动失效。任一失败都不得继续写新章或声称修订完成。
11. **接纳摘要与声音画像同步**：被修正文存在 `追踪/章节提交/第NNN章.json` 时，按 `chapter-acceptance-and-doctor.md` 运行 `chapter_candidate.py sync`，让合法修订后的正文摘要进入回执与投影日志；随后运行 `voice_profile.py update` 和 `story_doctor.py`。声音画像中的无回执旧章样本发生变化时，工具不得静默吸收，必须重新顺序冷读受影响范围并由作者再次确认 `LEGACY_APPROVED`。接纳摘要和画像摘要没有闭环前，不得恢复日更。

---

## Step 6：质量检查

对修改后的章节执行 Phase 5 质量检查（至少包含）：

1. **禁用词扫描**：如 Step 5 未覆盖全章，再次扫描
2. **正文元信息扫描**：同「级联检查」中的「正文元信息扫描」，确认覆盖全章。
3. **人物一致性**：修改后的角色行为是否与角色设定一致
4. **节奏检查**：修改是否破坏了章节节奏
5. **确定性语言复扫**：运行 `node scripts/check-degeneration.js --check --language=zh --fail-on=blocking 正文/第{X}章_*.md`；英文句段/裸英文词和其他 blocking 都只重写受影响句/段并复扫到 0，语言类 advisory 只有在用户/设定或白名单确认后才保留。

> 完整检查清单见 [Phase 5：质量检查](../SKILL.md#phase-5质量检查)。

## 常见问题

| 问题 | 处理 |
|------|------|
| 用户没说改哪里 | 问"你想改哪一章？哪方面？情节/节奏/对话/描写？" |
| 修改后字数暴增/暴减 | 提醒用户，由用户决定是否调整 |
| 连续改多章 | 逐章修改，每章独立执行 Step 3-6 |
| 改完发现后续不一致 | 语义冲突必须纳入本轮影响清单并统一；只有无冲突的 S3/S4 风格建议可排期 |
